# 性能の確認範囲

**動作テストの成功は、速度・同時接続数・長期利用・端末負荷の保証ではありません。**
この文書は、架空データだけを使ったローカル計測と、コードから確認できる制限を分けて記録します。

## 測定方法

ソースと依存関係を確認してから、次を実行できます。

```sh
node scripts/benchmark-performance.mjs
```

- 2026-10-25、Node.js 24.22.1、SQLite 3.53.4、Linux x64。CPU は AMD EPYC 9V74、実行環境から見える並列度は 9。
- 実際の `TaskStore` と配布スキーマを読み込み、ケースごとに新しいインメモリー SQLite を作成。データはその場で生成する架空の文字列のみ。
- 時間には DB 読み取り・戻り値への変換・`JSON.stringify` を含みます。各処理は初回 1 回と反復 25 回を計測し、反復の中央値と p95 を示します。
- 「初回」はデータ投入後の最初の読み取りです。Worker のコールドスタートではありません。
- ネットワーク、Cloudflare D1/R2、ディスク永続化、HTTP ヘッダー、圧縮、ブラウザー描画、画像の端末側変換、同時利用者は測っていません。
- ミリ秒はこの環境だけの結果です。単一プロセスで逐次実行した短いマイクロベンチマークであり、安定したサービス水準や対応件数の約束ではありません。
- バイト数はスクリプトが返却オブジェクトを JSON にした長さです。履歴は `task` / `page` などのメタデータも含みます。一覧の測定用オブジェクトは `tasks` と返信方式の設定だけで、ブラウザー API の表示名等や MCP の外側の包みは含みません。
- スクリプトは件数と戻り値の整合性を確認します。速度に合否のしきい値は設けていません。

## 変更前に確認した問題

以前の読み取りでは、部屋の履歴を全件返し、ブラウザーも全件を描画していました。返信待ちの高速更新で長い履歴を繰り返し取得すると、ローカル DB が速くても転送量と端末負荷が増えます。

| 架空データ | 変更前の処理 | 中央値 / p95 | JSON 本文 |
| --- | --- | --- | --- |
| 500 タスク・計 50,000 投稿 | 一覧読み取り | 11.398 / 14.355 ms | 250,456 bytes |
| 同上 | 返信待ち読み取り（返却上限 200 件） | 9.940 / 11.115 ms | 111,594 bytes |
| 1 部屋 1,000 投稿・各 256 文字（ASCII） | 履歴全件 | 4.268 / 7.640 ms | 549,679 bytes |
| 1 部屋 1,000 投稿・各 12,000 文字（ASCII） | 履歴全件 | 23.130 / 36.129 ms | 12,293,679 bytes |
| 1 部屋 1,000 投稿・各 12,000 文字（主に日本語） | 履歴全件 | 175.606 / 195.195 ms | 36,247,899 bytes |

12,000 文字のケースは、許可された長さの投稿を多数ためた負荷確認用です。一般的な使い方の代表値ではありません。日本語は同じ文字数でも UTF-8 の本文バイト数が大きくなるため、ASCII と分けています。

未圧縮の 549,679 bytes を毎秒取り直す単純計算では約 33.0 MB/分、日本語の長文ケースでは約 2.17 GB/分です。これは **応答本文の大きさ × 回数による理論値** で、実測の通信量や料金ではありません。実際の周期は要求完了後から数え、圧縮や通信待ちでも変わります。

## 改善後の再計測

以下を変更し、同じ条件で計測し直しました。

- 履歴は最新側から 1 ページ最大 100 投稿、メッセージ配列の JSON は 256 KiB 以内。ページ情報と過去へ進むカーソルを返し、表示中の範囲が全履歴ではないことを明示します。本文が長い場合は 100 件より少なくなります。
- 一覧の最新投稿は最大 400 Unicode コードポイントのプレビューに制限。原文は履歴ページに残り、削除しません。
- 返信待ちとタスク別の未読読み取りに合う索引を追加。全体の未読数は、その索引を使える集計に変更しました。
- assistant 画像の Base64 変換では、1 バイトずつのコールバックによるコピーを連続したループに変更。長さ・形式・正規の Base64 であることの検査は保持しています。
- 本人の投稿が返信済みになった後は、直後でも履歴の確認間隔を 5 秒に戻します。

### タスク一覧・返信待ち・未読

| 架空データ | 現在の処理 | 中央値 / p95 | JSON 本文 |
| --- | --- | --- | --- |
| 20 タスク・計 200 投稿 | 一覧 | 0.165 / 0.353 ms | 11,156 bytes |
| 100 タスク・計 10,000 投稿 | 一覧 | 1.156 / 2.397 ms | 55,756 bytes |
| 500 タスク・計 50,000 投稿 | 一覧 | 6.549 / 7.642 ms | 279,456 bytes |
| 同上 | 返信待ち（200 件返却） | 0.773 / 1.315 ms | 111,594 bytes |
| 同上 | 全体の未読数 | 2.433 / 2.966 ms | 5 bytes |

追加で、500 タスクそれぞれの最新投稿だけを 12,000 文字（主に日本語）にしたケースも計測しました。計 5,000 投稿の一覧は **9.198 / 11.082 ms、729,956 bytes** でした。最新投稿は 400 Unicode コードポイントのプレビューとして返します。短文ケースでもプレビューであることを示すメタデータが増えるため、変更前と本文サイズは一致しません。

SQLite の実行計画でも、返信待ちが全投稿の走査から索引検索に変わったこと、タスク別の未読集計がカバリング索引を使うことを確認しました。一覧全体の並べ替えは残っています。

### 長い履歴の最初のページ

| 1 部屋の架空データ | 今回返った投稿数 | 中央値 / p95 | JSON 本文 | 全件をたどるページ数 |
| --- | --- | --- | --- | --- |
| 1,000 投稿・各 256 文字（ASCII） | 100 | 0.871 / 1.799 ms | 55,672 bytes | 10 |
| 1,000 投稿・各 12,000 文字（ASCII） | 21 | 1.883 / 3.634 ms | 258,883 bytes | 48 |
| 1,000 投稿・各 12,000 文字（主に日本語） | 7 | 12.162 / 13.954 ms | 254,452 bytes | 143 |

3 ケースすべてで、カーソルを最後までたどると **重複・欠落なく 1,000 投稿** を取得できました。ページ分割は投稿を削除・省略する機能ではなく、一度に取得・表示する範囲を区切るものです。小さな会話ではページ情報や検査の分だけ処理と本文が増えるため、すべての読み取りが速くなるわけではありません。

現在の日本語長文ページを毎秒取得する単純計算は約 15.3 MB/分、5 秒ごとなら約 3.1 MB/分です。これも圧縮前本文だけの理論値です。全履歴が長くても 1 回の応答を抑えられますが、通信がゼロになるわけではありません。

### 画像の入力処理

同じ方法で作った、個人情報のない決定的なノイズ PNG をメモリー内だけで使用しました。画像生成時間、HTTP 転送、R2 保存、ブラウザーでのデコードは計測外です。

| 画像 | 処理 | 変更前の中央値 / p95 | 改善後の中央値 / p95 |
| --- | --- | --- | --- |
| 1,023 × 1,023 px、4,188,482 bytes | assistant Base64 変換と正規性検査 | 330.314 / 369.454 ms | 21.268 / 29.208 ms |
| 同上 | PNG ヘッダー・CRC 検査 | 10.057 / 10.789 ms | 9.478 / 10.104 ms |

Base64 は 5,584,644 文字です。画像検査を省略して速度を上げたわけではありません。64 × 64 px、16,521 bytes の小画像でも同じ経路を確認しています。

## 残る制限と運用上の注意

- タスク一覧は全件取得し、検索・状態での絞り込みもブラウザー側です。最新投稿は 400 Unicode コードポイントまでのプレビューです。検索対象はタイトル・概要・このプレビューであり、全履歴検索ではありません。多数の部屋や長い概要があれば応答は増えます。タスクが際限なく増えても軽い、とは言えません。
- 一覧 API は `TaskStore.listTasks` と設定取得の 2 回の DB 呼び出しですが、一覧 SQL 内にはタスクごとの未読数・最終投稿を求める相関サブクエリがあります。「2 回だからデータ量に関係なく一定時間」ではありません。
- 一覧は表示中に 15 秒ごと更新します。最新側の履歴は、最後の本人投稿から 5 分以内かつ未返信の間は 1 秒、それ以外は 5 秒が基本です。周期は要求完了後から数えます。非表示タブでは定期取得を止め、同一取得の重複を抑え、失敗時には間隔を延ばします。自動返信の実行速度を保証する仕組みではありません。
- 履歴のメッセージ配列には 256 KiB の予算がありますが、タスク情報等を加えた応答全体や、DB 内部で読むデータ量が常に同じ大きさになるわけではありません。SQL は最大 101 投稿を取得してからバイト予算に合わせて絞ります。日本語の最大長投稿では、この中間読み取りが数 MB になる場合があります。変更がなくても最新ページを取り直すため、差分配信による追加改善の余地があります。
- 過去ページでは定期更新を止め、画面も 1 ページだけを保持します。一部の履歴しか取得していない場合、未表示の返信まで自動で既読にはしません。最新ページの明示的な「確認済み」操作は、未表示の過去の返信も含むことを確認してから、そのページ取得時点までをまとめて確認済みにします。実際に全件を読んだ証明ではありません。それより後の返信と本人の未処理投稿には影響しません。
- 返信待ちの読み取りは 1 回 200 件までです。一度の応答にすべての待機投稿が含まれるとは限りません。
- 添付は 1 投稿 4 枚まで。ブラウザーの画像 API は 1 枚 6 MiB、assistant の画像入力は 1 枚 4 MiB までです。Base64 ではデータ量が約 4/3 に増えます。
- ブラウザーでは選択した画像を原則として長辺 2,048 px 以内へ変換します。画像準備は順番に、アップロードは最大 2 件並列です。これらの制限は、古いスマートフォンでの変換時間やメモリー不足を保証するものではありません。
- 送信済み画像は遅延読み込みですが、端末・回線・画像の内容によって表示時間は変わります。
- 複数利用者による共有サーバーの負荷試験はしていません。この雛形は 1 人ごとに独立した非公開環境を作る前提です。

実際の使用環境で、少量から投稿・画像・履歴の応答と端末負荷を確認してください。計測した件数を「安全な最大容量」として扱わず、履歴が増える場合は一覧のページ分割や差分配信も検討します。
